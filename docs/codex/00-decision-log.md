# 项目决策日志

## D001：首版模板范围
日期：2026-05-06  
决策：P0 首版只做合同管理、费用报销、采购申请三个样板应用。  
原因：覆盖主表、子表、流程、权限、台账、附件等核心能力。  

## D002：部署策略
日期：2026-05-06  
决策：P0 优先私有化单租户，架构预留 SaaS 多租户。  

## D003：数据存储策略
日期：2026-05-06  
决策：P0 使用元数据表 + 通用业务记录表 + JSON + 索引字段。

## D004：P0 系统架构策略
日期：2026-05-06  
决策：P0 采用模块化单体优先的架构形态，代码按领域模块拆分，物理部署可先保持单体；运行态必须通过已发布 Metadata Snapshot 驱动；系统架构文档按设计态、发布态、运行态和核心服务边界形成 v1.1 增强基线版。  
原因：降低 P0 私有化交付与研发复杂度，同时保留后续微服务化、SaaS 多租户与元数据 DSL 演进空间。

## D005：P0 系统架构增强目录基线
日期：2026-05-06  
决策：`20-system-architecture-design.md` 按 33 个正式章节增强，单独明确 P0 架构范围、不做范围、三态分层、核心服务设计、运行态渲染、权限链路、发布快照、回滚、技术选型、数据库/API 输入和 AI 生成约束。  
原因：为后续 `30-core-database-design.md`、API 文档和代码生成提供更稳定、可追溯、可执行的架构输入。

## D006：P0 核心数据库设计基线
日期：2026-05-06  
决策：`30-core-database-design.md` 采用 `lc_` 表名前缀，围绕租户与应用、组织用户角色、元数据与依赖、发布与运行、权限、通用业务数据、流程、文件、审计与安全九类表组形成 P0 核心数据库基线。业务对象数据统一进入 `lc_business_record`，高频检索字段进入 `lc_business_record_index`，已发布元数据进入不可变 `lc_metadata_snapshot`，运行态通过 `lc_app_runtime_pointer` 读取当前快照。  
原因：与 P0 已确认的“元数据表 + 通用业务记录表 + JSON + 索引字段”策略保持一致，同时为 API 设计、ORM 代码生成、发布回滚、流程版本锁定和权限审计提供稳定数据基础。

## D007：P0 核心 API 设计基线
日期：2026-05-06  
决策：`40-api-design.md` 采用 `/api/v1` 统一路径，按认证、应用中心、组织用户角色、设计态元数据、权限、发布回滚、运行态模型、业务数据、流程、文件、审计安全、回收站和诊断等 API 域划分。设计态 API、发布态 API、运行态 API 必须隔离；运行态 API 必须通过 `lc_app_runtime_pointer` 加载 `lc_metadata_snapshot`，不得读取 `lc_metadata_resource.draft_json`；业务记录写入、审批、发布、回滚和附件下载必须执行后端权限校验、事务控制、审计和必要的幂等控制。  
原因：为后续 OpenAPI、后端服务设计、前端运行态渲染器和测试用例生成提供统一接口基线，避免设计态草稿、运行态快照、权限校验和通用业务数据访问在 API 层出现口径分裂。


## D008：P0 技术栈与工程脚手架基线
日期：2026-05-06  
决策：`45-tech-stack-and-scaffold-decision.md` 采用单仓库 Monorepo，前端基线为 React + TypeScript + Vite + Ant Design，后端基线为 Java + Spring Boot + Maven，数据库优先 PostgreSQL，迁移工具使用 Flyway，缓存使用 Redis，文件存储通过本地文件与 S3 Compatible 适配层实现。P0 代码生成必须遵守该技术栈，不得自行替换前端框架、组件库、后端框架、数据库策略或工程结构。  
原因：为 Codex 后续生成前端界面、后端服务、API Client、Mock 数据、数据库迁移和测试用例提供稳定工程约束，避免在技术栈、目录结构、运行命令、接口调用和部署方式上出现口径分裂。

## D009：P0 前端运行态渲染器基线
日期：2026-05-06  
决策：`60-frontend-runtime-renderer-design.md` 将运行态前端定义为 RuntimeModel 驱动的通用渲染体系，运行态页面必须通过 `app_runtime_pointer` 对应的运行态模型加载 `snapshotId`、`appVersionId`、entities、forms、views、workflows 和 permissions。前端只做权限表现裁剪，后端仍是最终鉴权权威；列表、表单、详情、审批动作、附件均必须通过统一 Runtime Renderer、组件注册表和 API Client 实现。  
原因：保证 Codex 后续生成的前端不是固定业务 CRUD 页面，而是符合低代码平台特征的元数据驱动运行态，同时避免设计态草稿、运行态快照、权限裁剪、流程任务和文件鉴权在前端实现中出现口径分裂。

## D010：P0 前端页面与组件基线
日期：2026-05-06  
决策：`61-frontend-page-and-component-design.md` 将 P0 前端页面划分为认证、工作台、应用中心、模板、设计器、发布、运行态、任务、组织用户角色、审计安全和诊断等页面域；采用 React + TypeScript + Vite + Ant Design 的企业后台布局，运行态列表/表单/详情/审批必须复用 `60` 文档定义的 Runtime Renderer，页面调用必须经过统一 API Client 或 Mock Service。  
原因：为 Codex 生成可运行前端界面、路由、组件、Mock 数据和样板应用演示路径提供稳定输入，减少自由发挥导致的技术栈偏移、页面缺漏和运行态硬编码问题。


## D011：P0 前端运行态渲染器增强基线

原因：让 Codex 后续能够实现真正的元数据驱动运行态渲染器，避免生成普通 CRUD 页面、硬编码样板应用或忽略权限、版本冲突、异常边界和 Mock 场景。

## D013：P0 后端服务设计基线
日期：2026-05-06  
决策：`50-backend-service-design.md` 形成后端服务设计基线，P0 后端采用 Java + Spring Boot + Maven 的模块化单体结构，按 auth、tenant、app、org、metadata、permission、release、runtime、record、workflow、file、audit、recycle、diagnostics 等模块分包；Controller 只做协议适配，Application Service 负责用例编排、事务、权限入口、幂等入口和审计入口，Domain Service 承载领域规则，Repository 只做数据访问。发布、回滚、业务记录保存、流程审批、文件访问必须遵守统一事务、权限、审计和快照隔离约束。  
原因：为 Codex 后续生成后端代码、API 实现、服务测试和开发任务拆解提供可执行的服务边界，避免将业务逻辑堆入单一 Service、绕过运行态快照、跳过后端权限或错误生成业务对象专用表。

## D024：数据库接入采用 profile 与 Testcontainers 渐进验证
日期：2026-05-07  
决策：Phase 10 新增 `application-db.yml` 作为 PostgreSQL + Flyway 的 `db` profile，默认 profile 继续保持无数据库可启动；新增 Testcontainers PostgreSQL 测试验证 Flyway 迁移与最小 JDBC Repository。当前环境 Docker 不可用时容器测试允许跳过，但必须在 Docker 可用环境或 CI 中补跑。  
原因：既要让后端数据库迁移进入自动化测试路径，也要避免在本地未配置 PostgreSQL 或 Docker 时破坏现有 Mock 验收与基础后端测试。

## D025：Docker/Testcontainers 命令需在 Codex 中提升权限运行

原因：当前失败根因是 Codex 默认沙箱无法访问 Unix socket，不是 Docker 未安装、Docker Desktop 未启动或 Flyway/Testcontainers 代码失败。

## D026：审计安全幂等持久化采用可配置 Repository
日期：2026-05-07  
决策：审计日志、安全事件和幂等服务先抽象 Repository 接口，默认 profile 使用内存 Repository，`db` profile 下使用 JDBC Repository；后续运行态记录、文件、流程、权限也沿用可配置 Repository 方式渐进接入。  
原因：保持 Mock/默认开发环境轻量可跑，同时让 PostgreSQL/Flyway/Testcontainers 下的真实持久化逐步进入自动化验证，避免一次性切换全量数据库导致调试面过大。

## D027：运行态记录优先落通用记录表最小闭环
日期：2026-05-07  
决策：Phase 12 运行态记录后端先落地 `lc_business_record` 的创建、查询、列表、版本冲突更新，不为合同、报销、采购创建独立物理表；`snapshotId/appVersionId` 暂用 P0 默认值，后续再接 `lc_app_runtime_pointer`。  
原因：先验证通用业务记录表 + JSONB + 版本控制的核心数据路径，避免在发布快照、流程、权限、附件尚未完整接入前过早扩大业务复杂度。

## D028：运行态提交审批先落最小流程任务占位
日期：2026-05-07
