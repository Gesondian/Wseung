## 1. 文档目的

本文档用于定义低代码平台 P0 阶段的组织、用户与角色模块需求。

组织、用户与角色模块是权限系统、流程引擎、人员字段、部门字段、数据权限、审计日志和运行时访问控制的基础能力。

本文档重点回答：

```text
1. P0 需要支持哪些组织、用户、角色能力？
2. 组织树、部门负责人、用户状态、角色状态如何定义？
3. 用户与部门、用户与角色、部门与负责人的关系如何建立？
4. 流程中的“发起人上级”“发起人部门负责人”如何计算？
5. 数据权限中的“本人”“本部门”“本部门及下级”如何计算？
6. 人员选择、部门选择、字段权限和审计如何依赖本模块？
7. 后续 AI 生成数据库、API、页面、测试用例时应遵守什么边界？
```

本模块必须使用统一状态码：

```text

角色状态：active / disabled / deleted
```

### 0.4 统一权限规则

```text
1. 组织、用户、角色管理属于平台级或租户级管理权限。
2. 普通用户不能维护组织、用户、角色。
3. 角色分配、部门负责人变更、用户停用必须记录审计日志。
4. 运行态不直接修改组织用户角色数据。
5. 权限判定以 08-P0-permission-system.md 为准。
```

### 0.5 统一发布规则

组织、用户与角色属于平台基础主数据，P0 不纳入应用发布快照；但权限策略在发布运行时中需要引用本模块产生的 user、role、orgUnit 等主体标识。

## 2. 模块定位

组织、用户与角色模块是低代码平台的基础身份与组织模型模块。

它不直接负责业务应用搭建，也不直接负责业务数据权限计算结果的最终判定，但它为权限系统和流程引擎提供必要的身份、组织和角色数据。

本模块定位为：

```text
租户内组织架构管理中心
用户账号管理中心
角色定义与用户角色关系管理中心
流程参与人解析基础模块
数据权限范围计算基础模块
人员/部门字段数据源模块
审计日志操作者身份来源模块
```

## 3. 目标用户

| 用户类型 | 使用目标 |
|---|---|
| 平台管理员 | 初始化租户组织、用户、角色，维护基础主数据。 |
| 租户管理员 | 管理本租户组织、部门、人员和角色。 |
| IT 管理员 | 维护部门负责人、用户状态、角色关系，支持权限治理。 |
| 应用管理员 | 在配置权限和流程时选择用户、部门、角色。 |
| 实施/配置顾问 | 为样板应用配置审批人、数据范围和默认权限。 |
| 普通业务用户 | 被选择为流程处理人、申请人、数据责任人，不直接管理本模块。 |

---

## 4. 业务目标

P0 阶段，本模块需要支撑以下业务目标：

```text
1. 支持创建和维护租户内组织树。
2. 支持创建、启用、停用、删除用户。
3. 支持创建和维护角色。
4. 支持用户加入部门。
5. 支持用户绑定一个或多个角色。
6. 支持部门负责人设置。
7. 支持流程按部门负责人、发起人上级、角色、指定用户解析处理人。
8. 支持数据权限按本人、本部门、本部门及下级计算范围。
9. 支持人员字段、部门字段、审批人选择器读取用户和部门。
10. 支持关键操作审计。
```

## 5A. P0 必做清单详表（执行版）

文档版本：v1.2  
更新日期：2026-05-06  
适用范围：`03-P0-org-user-role.md`  

本章节用于把组织、用户与角色模块从“能力描述”细化为可研发、可测试、可由 AI 后续生成代码和接口的 P0 执行清单。本模块是权限、流程处理人、人员/部门字段、审计归属、数据权限计算的基础设施。


### 5A.1 P0 功能点描述统一要求

本章节中的每一个 P0 功能点都必须满足以下描述规范，后续 AI 生成页面、API、数据库、测试用例和开发任务时必须直接引用功能编号。

| 描述项 | 要求 |
|---|---|
| 功能编号 | 使用 `P0-模块缩写-序号`，序号三位递增。 |
| 所属分类 | 标明该功能归属的业务分类，便于研发分包。 |
| 用户角色 | 标明主要使用者，不能只写“用户”。 |
| 业务目标 | 说明为什么需要该功能。 |
| 前置条件 | 说明功能执行前必须存在的数据、权限或状态。 |
| 输入内容 | 说明页面、接口或配置需要输入哪些字段。 |
| 处理逻辑 | 说明服务端、前端或运行时需要执行的关键逻辑。 |
| 输出结果 | 说明功能执行后产生什么数据、状态或页面变化。 |
| 权限要求 | 说明该功能需要经过哪些权限校验。 |
| 审计要求 | 说明是否需要写入审计日志以及记录内容。 |
| 异常处理 | 说明常见失败场景及系统反馈。 |
| 验收标准 | 说明测试可以如何判断该功能完成。 |

### 5A.2 P0 功能点优先级规则

| 优先级 | 含义 | 处理原则 |
|---|---|---|
| P0-Must | 没有该功能，主业务闭环不可运行。 | 必须随 P0 首版交付。 |
| P0-Should | 没有该功能，主业务闭环仍可运行，但交付体验明显下降。 | 原则上纳入 P0，资源紧张时可降级但必须保留入口。 |
| P0-Guardrail | 不是直接业务功能，但用于安全、审计、发布稳定性。 | 必须纳入 P0，不可后补。 |

### 5A.4 P0 组织、用户与角色必做功能明细

#### P0-OUR-001 组织用户角色管理入口

| 描述项 | 内容 |
|---|---|
| 所属分类 | OUR-C01 / OUR-C02 / OUR-C03 |
| 用户角色 | 平台超级管理员、企业管理员、IT 管理员 |
| 业务目标 | 提供统一入口管理组织、用户、角色，避免权限、流程和人员字段分散配置。 |
| 前置条件 | 当前用户已登录，且具备平台级或租户级组织管理权限。 |
| 输入内容 | 无必填输入；可输入搜索关键词。 |
| 处理逻辑 | 页面展示组织树、用户列表、角色列表三个主入口；默认进入组织树视图；所有入口都必须带 tenantId 上下文。 |
| 输出结果 | 用户可进入部门管理、用户管理、角色管理和关系维护页面。 |
| 权限要求 | 需要 `platform.org.manage` 或 `tenant.org.manage` 权限。 |
| 审计要求 | 入口访问不强制审计；后续增删改操作必须审计。 |
| 异常处理 | 无权限时展示无权限页面；组织服务异常时展示重试入口。 |
| 验收标准 | 管理员可从一个页面进入组织、用户、角色三个管理区域。 |

#### P0-OUR-002 组织树展示

| 描述项 | 内容 |
|---|---|
| 所属分类 | OUR-C01 |
| 用户角色 | 平台超级管理员、企业管理员、应用管理员、实施顾问 |
| 业务目标 | 展示企业部门层级，为用户归属、流程上级、数据权限提供基础。 |
| 前置条件 | 租户存在根组织。 |
| 输入内容 | tenantId、关键词、状态筛选。 |
| 处理逻辑 | 按父子关系加载部门树；支持展开/收起；默认展示 active 部门；disabled 部门可灰显；deleted 部门不展示。 |
| 输出结果 | 部门树节点包含 orgUnitId、orgUnitName、parentId、负责人、人数、状态。 |
| 权限要求 | 具备组织查看权限即可查看组织树；管理操作需更高权限。 |
| 审计要求 | 查看不审计；导出组织树需审计。 |
| 异常处理 | 组织树循环引用时后端拒绝返回异常结构并记录错误日志。 |
| 验收标准 | 可正确展示至少三级部门结构，并支持按部门名称搜索。 |

#### P0-OUR-003 创建部门

| 描述项 | 内容 |
|---|---|
| 所属分类 | OUR-C01 |
| 用户角色 | 企业管理员、IT 管理员 |
| 业务目标 | 支持企业初始化和调整组织结构。 |
| 前置条件 | 已选择父级部门；父级部门状态为 active。 |
| 输入内容 | 部门名称、部门编码、上级部门、部门负责人、排序号、描述。 |
| 处理逻辑 | 校验同级部门编码唯一；创建后状态默认为 active；负责人必须是当前租户 active 用户。 |
| 输出结果 | 新增一条组织单元记录，并刷新组织树。 |
| 权限要求 | 需要 `orgUnit.create` 权限。 |
| 审计要求 | 记录创建人、创建时间、部门名称、父部门、负责人。 |
| 异常处理 | 编码重复、父部门不存在、负责人无效时阻止提交并提示。 |
| 验收标准 | 管理员可创建部门，并立即在组织树中看到该部门。 |

#### P0-OUR-004 编辑部门

| 描述项 | 内容 |
|---|---|
| 所属分类 | OUR-C01 |
| 用户角色 | 企业管理员、IT 管理员 |
| 业务目标 | 支持调整部门名称、负责人、排序和描述。 |
| 前置条件 | 部门存在且未被删除。 |
| 输入内容 | 部门名称、部门编码、负责人、排序号、描述。 |
| 处理逻辑 | 部门编码变更需校验唯一；根部门不允许修改父级；负责人变更需同步影响流程找人规则。 |
| 输出结果 | 部门信息更新，更新时间和更新人写入。 |
| 权限要求 | 需要 `orgUnit.update` 权限。 |
| 审计要求 | 记录修改前后差异，尤其负责人变化。 |
| 异常处理 | 部门被禁用时允许编辑基础信息但不允许设置为流程处理部门。 |
| 验收标准 | 修改部门负责人后，流程“发起人部门负责人”能读取最新负责人。 |

#### P0-OUR-005 停用/启用部门

| 描述项 | 内容 |
|---|---|
| 所属分类 | OUR-C01 |
| 用户角色 | 企业管理员、IT 管理员 |
| 业务目标 | 在不删除历史数据的前提下禁用部门。 |
| 前置条件 | 部门存在且未删除；根部门不允许停用。 |
| 输入内容 | orgUnitId、目标状态、停用原因。 |
| 处理逻辑 | 停用部门后，该部门不可作为新用户主部门，不可作为新权限范围；历史数据仍保留部门引用。 |
| 输出结果 | 部门状态变为 disabled 或 active。 |
| 权限要求 | 需要 `orgUnit.disable` 或 `orgUnit.enable` 权限。 |
| 审计要求 | 记录状态变更、操作人、原因。 |
| 异常处理 | 存在 active 子部门时，系统提示是否先处理子部门；P0 可禁止直接停用。 |
| 验收标准 | 停用部门后，新增用户页面不可选择该部门作为主部门。 |

#### P0-OUR-006 删除部门（软删除）

| 描述项 | 内容 |
|---|---|
| 所属分类 | OUR-C01 |
| 用户角色 | 企业管理员、IT 管理员 |
| 业务目标 | 删除不再使用的部门，同时保留历史审计和业务数据关联。 |
| 前置条件 | 部门下无 active 子部门；部门下无 active 用户作为主部门。 |
| 输入内容 | orgUnitId、删除原因。 |
| 处理逻辑 | 执行软删除，写入 deletedAt、deletedBy、isDeleted；历史记录仍可展示部门快照名称。 |
| 输出结果 | 部门从组织树隐藏。 |
| 权限要求 | 需要 `orgUnit.delete` 权限。 |
| 审计要求 | 记录删除人、删除时间、删除原因。 |
| 异常处理 | 存在用户或子部门时禁止删除，并提示迁移。 |
| 验收标准 | 删除部门不会导致历史审批单、合同台账中的部门名称丢失。 |

#### P0-OUR-007 设置部门负责人

| 描述项 | 内容 |
|---|---|
| 所属分类 | OUR-C01 / OUR-C05 |
| 用户角色 | 企业管理员、IT 管理员、实施顾问 |
| 业务目标 | 支撑流程中的“发起人上级”“部门负责人”找人规则。 |
| 前置条件 | 部门存在且 active；负责人用户 active。 |
| 输入内容 | orgUnitId、负责人 userId，可选副负责人。 |
| 处理逻辑 | P0 默认一个主负责人；如果配置多个负责人则按列表返回，流程节点可全部处理或取第一个，具体由流程规则决定。 |
| 输出结果 | 部门负责人关系保存。 |
| 权限要求 | 需要 `orgUnit.manager.update` 权限。 |
| 审计要求 | 记录负责人新增、删除、替换前后差异。 |
| 异常处理 | 负责人被禁用后，流程发布校验需提示该部门负责人无效。 |
| 验收标准 | 报销流程配置“发起人部门负责人”后能正确生成待办。 |

#### P0-OUR-008 用户列表展示与搜索

| 描述项 | 内容 |
|---|---|
| 所属分类 | OUR-C02 |
| 用户角色 | 企业管理员、IT 管理员、应用管理员 |
| 业务目标 | 支持管理员查看、检索和维护企业用户。 |
| 前置条件 | 当前用户具备用户查看权限。 |
| 输入内容 | 关键词、部门筛选、角色筛选、状态筛选。 |
| 处理逻辑 | 列表分页展示用户；支持按姓名、账号、手机号、邮箱搜索；默认隐藏 deleted 用户。 |
| 输出结果 | 用户列表包含 userId、姓名、账号、主部门、角色摘要、状态、更新时间。 |
| 权限要求 | `user.view`；仅能查看授权范围内用户。 |
| 审计要求 | 普通查询不审计；导出用户列表审计。 |
| 异常处理 | 查询条件过宽时必须分页，不允许一次返回全量。 |
| 验收标准 | 管理员可按部门和状态筛选用户。 |

#### P0-OUR-009 创建用户

| 描述项 | 内容 |
|---|---|
| 所属分类 | OUR-C02 |
| 用户角色 | 企业管理员、IT 管理员 |
| 业务目标 | 为员工、实施顾问或业务用户创建平台账号。 |
| 前置条件 | 主部门存在且 active。 |

### 5A.5 P0 组织用户角色完成定义 Definition of Done

本模块达到 P0 完成标准，必须同时满足：

```text
1. 可以创建、编辑、停用、删除部门，并维护部门负责人。
2. 可以创建、编辑、启用、禁用、锁定、删除用户。
3. 可以创建、编辑、停用自定义角色，并分配用户。
4. 用户必须有主部门，数据权限和流程找人默认按主部门计算。
5. 人员选择器和部门选择器可以被表单、流程、权限模块复用。
6. 流程可以通过部门负责人规则找到审批人。
7. 权限系统可以通过用户角色关系判断访问权限。
8. 所有写操作必须记录审计日志。
9. 删除均为软删除，历史业务数据和审计记录不能丢失。
10. API / DSL 使用 camelCase，数据库字段使用 snake_case。
```

## 7. 核心概念定义

### 7.1 租户 Tenant

租户是组织、用户、角色和业务数据的隔离边界。

P0 优先私有化单租户部署，但所有组织、用户、角色表必须包含 tenantId / tenant_id。

### 7.2 组织单元 Org Unit

组织单元代表企业内部门、子部门或组织节点。

P0 组织树采用树形结构：

```text
总部
├── 法务部
├── 财务部
├── 采购部
└── 销售部
```

组织单元必须支持上级组织关系。

### 7.3 部门负责人 Department Leader

部门负责人用于支撑：

```text
流程审批中的“发起人部门负责人”
数据权限中的“本部门负责人可见”
人员字段默认值
```

P0 一个部门可以设置一个主负责人，P1/P2 可扩展多个负责人或负责人类型。

### 7.4 用户 User

用户是平台登录、应用访问、流程处理、数据归属、审计记录的主体。

用户可以属于一个主部门，并可预留多个部门关系。

P0 推荐：

```text
主部门：用于流程上级、默认数据归属、数据权限计算
扩展部门：预留，不作为 P0 复杂规则依据
```

### 7.5 角色 Role

角色是权限分配的主要载体。

角色可分为：

```text
平台内置角色
租户自定义角色
应用内置角色
应用自定义角色
```

P0 角色与权限策略的最终绑定以权限系统为准。

### 7.6 用户角色 User Role

用户角色表示某个用户拥有某个角色。

一个用户可以拥有多个角色。

### 7.7 授权主体 Principal

Principal 是权限系统中的授权主体，来源于本模块。

P0 支持：

```text
user
role
orgUnit
```


### 8.2 租户管理员创建用户

作为租户管理员，我希望创建业务用户，并为其分配部门和角色，以便用户可以访问对应应用。

验收：

```text
1. 可创建用户并分配主部门。
2. 可给用户分配一个或多个角色。
3. 用户创建后可登录或被授权访问应用。
```

### 8.3 IT 管理员停用离职用户

作为 IT 管理员，我希望停用离职用户，避免其继续访问系统，同时保留其历史审批和审计记录。

验收：

```text
1. 停用用户不能登录。
2. 停用用户的历史数据和流程记录仍可展示。
3. 停用操作写入审计日志。
```

### 8.4 应用管理员选择审批角色

作为应用管理员，我希望在配置流程节点时选择角色或部门负责人作为审批人，以便流程能动态路由。

验收：

```text
1. 流程节点可选择指定用户、角色、部门负责人。
2. 流程发起时可解析出具体处理人。
3. 解析失败时阻止发起并提示原因。
```

### 8.5 业务用户填写人员字段

作为业务用户，我希望在表单中选择人员或部门，以便记录负责人、经办人或归属部门。

验收：

```text
1. 人员选择器只展示 active 用户。
2. 部门选择器只展示 active 组织单元。
```

## 13. 业务规则

### 13.1 编码规则

```text
orgUnitKey：同一租户唯一，建议小写字母、数字、下划线。
userAccount：同一租户唯一。
roleKey：同一租户唯一。
```

### 13.2 删除规则

```text
1. 所有删除均为软删除。
2. 被流程、权限、数据引用的组织、用户、角色删除前必须提示影响。
3. 历史记录中的用户名称、部门名称、角色名称应保留快照或可通过历史数据追溯。
```

### 13.3 历史数据规则

```text
1. 用户改名不应影响历史审计中的操作者标识。
2. 用户换部门不应自动修改历史业务记录归属部门。
3. 角色改名不应影响历史审计中记录的角色快照。
```

### 13.4 流程解析规则

```text
1. 指定用户：直接生成该用户待办，用户必须 active。
2. 指定角色：解析角色下 active 用户。
3. 指定部门：解析部门下 active 用户，P0 不建议直接给整个部门全员生成待办，需谨慎配置。
4. 发起人部门负责人：按发起人主部门查找负责人。
5. 发起人上级：P0 可等同发起人部门负责人；如企业有汇报关系，P1/P2 再扩展。
```

### 13.5 数据权限规则

```text
本人：createdBy 等于当前用户。
本部门：record.departmentId 等于当前用户主部门。
本部门及下级：record.departmentId 在当前用户主部门及其子部门集合内。
指定角色：当前用户拥有对应 roleId。
全部数据：拥有全量数据权限。
```

## 14. 异常处理

### 14.1 组织删除失败

触发条件：

```text
存在 active 子部门
存在 active 用户
被权限策略引用
被流程规则引用
```

处理方式：

```text
阻止删除
展示依赖明细
提示先解除依赖
记录失败日志
```

### 14.2 用户停用存在待办

触发条件：

```text
用户存在 pending 任务
```

处理方式：

```text
允许停用但必须提示风险
P0 不自动转交
后续流程处理需要由管理员人工处理或恢复用户
```

### 14.3 角色被权限策略引用

触发条件：

```text
停用或删除角色时，角色仍被权限策略引用
```

处理方式：

```text
展示引用应用和策略数量
要求确认
记录审计日志
```

### 14.4 部门负责人缺失

触发条件：

```text
流程节点要求发起人部门负责人，但发起人主部门未配置负责人
```

处理方式：

```text
阻止流程发起
提示缺失部门负责人
记录流程发起失败日志
```

### 14.5 用户无部门

触发条件：

```text
数据权限或流程规则需要用户主部门，但用户未设置主部门
```

处理方式：

```text
阻止相关操作
提示管理员补充用户部门
```

## 22. 验收标准

### 22.1 组织管理验收

```text
1. 可创建多级组织树。
2. 可设置部门负责人。
3. 可停用组织。
4. 可软删除组织。
5. 删除组织前能检查子部门、用户和权限引用。
```

### 22.2 用户管理验收

```text
1. 可创建用户并分配主部门。
2. 可给用户分配多个角色。
3. active 用户可被人员选择器选中。
4. disabled、deleted 用户不可作为新流程处理人。
5. 停用用户不影响历史审批和审计展示。
```

### 22.3 角色管理验收

```text
1. 可创建自定义角色。
2. 可给角色分配用户。
3. 角色可被权限系统引用。
4. 停用角色后不再参与新权限判定。
5. 删除角色前能检查用户绑定和权限引用。
```

### 22.4 流程与权限验收

```text
1. 流程节点可选择指定用户、角色、部门负责人。
2. 发起人部门负责人规则可正确解析处理人。
3. 数据权限可按本人、本部门、本部门及下级计算。
4. 人员字段和部门字段可正常读取本模块数据。
```

### 22.5 样板应用验收

```text
1. 合同管理可配置法务、财务、合同管理员角色。
2. 费用报销可按发起人部门负责人和财务角色流转。
3. 采购申请可按采购角色和财务角色流转。
```

## 24. 给 AI 生成代码/设计的提示

后续 AI 基于本文档生成内容时，必须遵守以下约束：

```text
1. 不要把组织、用户、角色逻辑写死在权限模块中。
2. 权限系统引用本模块产出的 user、role、orgUnit 作为 Principal。
3. 所有表必须预留 tenant_id。
4. 所有删除必须软删除。
5. 用户停用不能删除历史数据、流程记录和审计记录。
6. 人员选择器只能返回 active 用户。
7. 部门选择器只能返回 active 组织单元。
8. 角色停用后不参与新权限判定。
9. 流程中的发起人部门负责人必须基于用户主部门解析。
10. P0 不做完整 IAM、SSO、LDAP/AD、复杂岗位、矩阵组织。
11. 所有管理操作必须写审计日志。
12. 代码生成时应先实现组织树、用户、角色、用户角色关系，再与权限系统衔接。
```
