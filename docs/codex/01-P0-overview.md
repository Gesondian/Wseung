## 2. P0 阶段产品定位

P0 阶段的产品定位是：

> **面向企业内部管理应用的低代码搭建与流程自动化平台 MVP。**

P0 不追求完整企业级低代码平台的所有能力，而是先证明平台主干能力成立：

```text
应用
→ 数据对象
→ 表单
→ 视图/台账
→ 流程
→ 权限
→ 发布
→ 运行
→ 审计
→ 模板复用
```

P0 的核心目标是：**让实施顾问、业务管理员和 IT 管理员可以通过可视化配置，稳定搭建并运行合同管理、费用报销、采购申请三类真实企业应用。**

## 3. P0 成功标准

P0 成功的判断标准不是“功能数量多”，而是能否跑通真实业务闭环。

| 维度 | P0 成功标准 |
|---|---|
| 建模能力 | 可创建业务对象、字段、子表、关联对象，并能发布生效。 |
| 表单能力 | 可拖拽生成录入、编辑、查看和审批表单。 |
| 视图能力 | 可生成列表、详情、台账，支持筛选、搜索、排序和基础批量操作。 |
| 流程能力 | 可配置常见审批流，支持审批、抄送、条件分支、驳回、撤回和流程日志。 |
| 权限能力 | 可控制应用、对象、数据、字段和流程节点权限。 |
| 发布能力 | 草稿修改不影响线上运行版本，支持发布、停用和回滚。 |
| 运行能力 | 运行端根据已发布元数据渲染表单、视图、详情和审批页面。 |
| 模板能力 | 可从合同、报销、采购模板创建应用并二次编辑。 |
| 审计能力 | 关键配置、权限、数据、流程、导入导出操作均可追踪。 |
| 交付能力 | 能在私有化单租户环境中完成部署和业务验证。 |

## 4. P0 业务闭环

P0 必须优先跑通以下端到端闭环：

```text
1. 管理员创建组织、用户和角色
2. 实施顾问进入应用中心创建应用
3. 搭建者创建业务对象和字段
4. 搭建者配置表单布局和字段规则
5. 搭建者配置列表、详情和台账视图
6. 搭建者配置审批流程
7. 管理员配置应用、对象、数据、字段和流程节点权限
8. 搭建者发布应用版本
9. 业务用户进入运行端填写表单并提交
10. 系统创建业务数据和流程实例
11. 审批人处理待办并填写审批意见
12. 流程完成后业务数据状态更新
13. 用户在台账中查看授权范围内的数据
14. 管理者查看基础看板
15. 管理员查看审计日志和操作记录
16. 应用或资源删除后进入回收站，可按权限恢复
```

只要该闭环稳定，后续 P1/P2/P3 的动作流、连接器、数据集、高级报表、插件市场和 AI 能力都可以在此基础上扩展。

## 6. P0 不做范围

P0 必须严格控制范围，不得在模块设计中隐性加入以下能力。

| 不做内容 | 处理方式 |
|---|---|
| 完整 ERP | P0 只提供搭建合同、采购、报销等应用的能力，不做完整行业套件。 |
| 完整 BI | P0 只做轻量看板和基础报表，不做复杂交叉分析和专业 BI。 |
| 完整 BPMN | P0 只做企业审批流，不兼容全量 BPMN 标准。 |
| 会签、并行、加签、转交 | 不作为 P0，后续 P1/P2 评估。 |
| 在线 IDE | P0 不提供完整代码开发、调试、打包和发布。 |
| 插件市场 | P0 只预留扩展点，不做市场、审核、上架、安装、计费。 |
| 复杂 AI | P0 不承诺自然语言一键生成完整应用，AI 放到 P3。 |
| 原生 App | P0 支持 PC 和移动端 H5 自适应，不做 iOS/Android 原生 App。 |
| 企业微信/钉钉/飞书深度集成 | P0 只预留，完整集成放 P1/P2。 |
| 复杂数据加工/ETL | P0 不做完整数据加工引擎，P1/P2 再扩展数据集和 ETL。 |
| 复杂脚本沙箱 | P0 不开放任意脚本执行，避免安全和稳定性风险。 |

## 7. P0 模块依赖关系

P0 模块不是并列独立实现，而是存在明确依赖。

```text
组织、用户与角色
        ↓
权限系统 ← 应用中心
        ↓       ↓
数据对象建模 → 表单设计器 → 视图/台账
        ↓              ↓       ↓
        └────────→ 流程审批引擎
                       ↓
发布、版本与运行时
        ↓
样板应用运行验证
        ↓
审计日志与回收站
```

关键依赖说明：

| 依赖项 | 说明 |
|---|---|
| 权限依赖组织用户角色 | 数据权限、审批处理人、字段权限都需要用户、部门、角色作为基础。 |
| 表单依赖数据对象 | 表单组件必须绑定对象字段，不能脱离数据模型独立存在。 |
| 视图依赖对象和权限 | 列表与详情必须基于对象字段，并按数据权限过滤。 |
| 流程依赖表单和权限 | 流程发起、审批表单、节点字段权限都依赖表单和权限模型。 |
| 发布依赖完整性校验 | 应用必须校验对象、表单、流程、权限等配置完整后才能发布。 |
| 运行时依赖已发布元数据 | 运行端只读取已发布版本，不读取草稿配置。 |
| 审计贯穿全链路 | 配置、权限、发布、数据、流程、导入导出均要写审计。 |

## 8. P0 核心状态模型

### 8.1 应用状态

```text
草稿
→ 已发布
→ 已停用
→ 已删除/回收站
→ 已恢复
```

规则：

- 草稿态仅设计端可见，不影响运行端。
- 已发布应用可被授权用户访问。
- 已停用应用运行端不可访问，但配置和数据保留。
- 已删除应用进入回收站，不立即物理删除。
- 恢复应用后应回到删除前状态或指定为停用状态，由模块设计明确。

### 8.2 业务数据状态

```text
草稿
→ 审批中
→ 已通过
→ 已驳回
→ 已撤回
→ 已作废
→ 已归档
```

规则：

- 非流程数据可直接进入有效/已保存状态。
- 流程表单提交后进入审批中。
- 流程结束后根据结果更新为已通过、已驳回或已归档。
- 作废不等于删除，作废数据仍应可审计。

### 8.3 流程实例状态

```text
未发起
→ 运行中
→ 已通过
→ 已驳回
→ 已撤回
→ 已作废
→ 异常
```

规则：

- 每个流程实例必须绑定业务记录、流程定义版本和发起人。
- 审批任务必须记录处理人、处理时间、处理意见和处理结果。
- 流程异常必须可查询、可定位，不得静默失败。

### 8.4 发布版本状态

```text
草稿版本
→ 待发布校验
→ 发布成功
→ 发布失败
→ 历史版本
→ 回滚版本
```

规则：

- 发布失败不得影响当前线上运行版本。
- 每次发布必须生成版本号和变更摘要。
- 回滚必须记录操作人、时间、目标版本和原因。

## 9. P0 统一数据与元数据原则

P0 必须遵循元数据驱动原则，所有关键配置都应可序列化、可发布、可导出。

### 9.1 必须元数据化的对象

```text
应用元数据
对象元数据
字段元数据
表单元数据
视图元数据
流程元数据
权限元数据
看板元数据
模板元数据
发布版本元数据
```

### 9.2 业务数据存储策略

P0 采用以下策略：

> **元数据表 + 通用业务记录表 + JSON 数据字段 + 可索引字段扩展。**

业务记录建议包含以下公共字段：

```text
record_id
tenant_id
app_id
object_id
version_id
data_json
status
created_by
created_at
updated_by
updated_at
deleted_at
```

### 9.3 数据策略边界

- P0 不面向单对象千万级数据管理。
- 所有列表查询必须分页。
- 高频筛选字段应支持配置为索引字段。
- 删除字段采用软删除，不直接清除历史数据。
- 复杂报表、大数据分析、OLAP 和宽表优化放到后续版本。

## 10. P0 权限总原则

P0 权限必须从第一版开始内建，不能后补。

### 10.1 权限模型

P0 采用：

```text
RBAC
+ 数据范围
+ 字段权限
+ 流程节点权限
```

### 10.2 权限层级

| 权限层级 | 控制内容 |
|---|---|
| 平台级权限 | 用户、组织、角色、系统配置、审计、回收站。 |
| 应用级权限 | 应用管理、应用设计、应用使用、应用只读。 |
| 对象级权限 | 查看、新增、编辑、删除、导入、导出。 |
| 数据级权限 | 本人、本部门、本部门及下级、全部、自定义条件。 |
| 字段级权限 | 可见、不可见、只读、可编辑、脱敏。 |
| 流程节点权限 | 不同流程节点上的字段可见、可编辑、必填。 |

### 10.3 权限实现约束

- 前端隐藏不等于权限控制，后端接口必须重复校验权限。
- 导入、导出、批量操作必须受权限控制。
- 审批页字段权限必须同时受字段权限和流程节点权限影响。
- 权限变更必须写入审计日志。
- 超级管理员权限需要可追踪，不得绕过审计。

## 14. P0 对 AI 后续生成的统一约束

后续 AI 生成模块需求、架构、数据库、API、页面、测试用例和代码骨架时，必须遵循以下约束。

### 14.1 范围约束

- 不得把 P1/P2/P3 能力写成 P0 必交付。
- 不得引入完整 BPMN、完整 BI、在线 IDE、插件市场、复杂 AI、原生 App。
- 所有新增能力必须说明属于 P0、P1、P2 还是 P3。
- 若发现功能超出 P0，应标注为“后续扩展”，不得混入 P0 验收。

### 14.2 架构约束

- 所有核心能力必须元数据驱动。
- 设计态与运行态必须隔离。
- 运行端只能读取已发布版本。
- 关键配置必须支持版本化。
- 所有接口必须考虑 `tenant_id`、`app_id`、`version_id`。
- 所有删除优先软删除。
- 所有关键操作必须写审计日志。

### 14.3 数据约束

- P0 采用通用记录表 + JSON 数据字段。
- 列表查询必须分页。
- 高频查询字段必须考虑索引字段方案。
- 导入导出必须受权限控制。
- 字段删除、对象删除、应用删除必须考虑历史数据解释和恢复。

### 14.4 权限约束

- 前后端都必须执行权限控制。
- 字段权限、数据权限、流程节点权限不能只在 UI 层实现。
- 导出、导入、批量操作、附件下载必须单独校验权限。
- 超级管理员操作也必须审计。

### 14.5 输出格式约束

AI 后续产出模块文档时，建议统一包含以下章节：

```text
1. 模块定位

```

## 15. P0 总体验收清单

| 验收项 | 通过标准 |
